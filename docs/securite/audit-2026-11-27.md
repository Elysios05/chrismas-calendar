# Audit de sécurité — 27 novembre 2026

Équipe Sécurité, avant l'ouverture des salons au public. Code audité : `main` au commit `8c3dac4`.
Base auditée : projet Supabase réel, **en lecture seule** (politiques, droits, fonctions, conseiller de sécurité,
code des Edge Functions déployées, identique au dépôt). Correctifs SQL proposés, non appliqués :
[`correctifs-proposes.sql`](correctifs-proposes.sql).

## Résumé pour non-spécialiste

1. **Aucune fuite entre couples n'a été trouvée** : un salon ne peut ni lire ni modifier les lettres, photos,
   jeux ou réglages d'un autre salon, et les cases préparées restent illisibles avant leur jour.
2. **Le vrai risque, c'est la panne** : une seule personne malveillante peut, sans compétence particulière,
   remplir les 50 places (« Complet ») ou saturer la base et le stockage gratuits, ce qui arrête le site pour tout le monde.
3. Une personne qui connaît le lien de connexion d'un salon peut lire **l'adresse e-mail** donnée à la création.
4. Les souvenirs personnels d'Alexandre et Flavie retirés le 26 nov sont **toujours lisibles dans l'historique** du dépôt public.
5. Il manque une page de confidentialité (RGPD) et un moyen de supprimer son calendrier.

**À faire avant d'ouvrir** : SEC-01, SEC-02, SEC-03 (Backend), puis SEC-04 à SEC-08.

## Constats

Gravité : **Élevée** = un inconnu peut nuire à tous les utilisateurs ou à leurs données sans condition rare ;
**Moyenne** = nuisance réelle mais limitée (une seule personne, condition préalable, ou conformité) ;
**Faible** = défense en profondeur, conditions improbables ; **Info** = à savoir.
Aucun constat **Critique**.

## Vérifié et jugé sûr

- **Isolation entre salons** : toutes les politiques RLS (lues dans la base réelle) filtrent par `my_salon()` ;
  écritures impossibles dans un autre salon (`salon_id` vérifié en `with check`) ; `profiles`, `app_settings`
  sans écriture depuis le site ; `salons` : seule la colonne `config` est modifiable (droit de colonne vérifié),
  donc pas de `day_override` côté client ; `salon_invitations`, `salon_creations`, `reminder_log` illisibles.
- **Cases préparées** : lecture par le destinataire seulement à partir du jour J calculé par le serveur ; gel
  dès l'ouverture appliqué par politique **et** déclencheur (contournement par `upsert`/`delete` impossible) ;
  photos d'une case gelée non supprimables ; pas de suppression de `progress` (donc pas de « dégel »).
- **Fonctions sensibles** (`salon_create`, `salon_join`, `salon_claim_invitation`, `salon_release_invitation`,
  `purge_salons_vides`, `supprimer_salon`, `reminder_targets`, `call_rappel_veille`) : réservées au serveur
  (vérifié avec `has_function_privilege`). Toutes les SECURITY DEFINER ont un `search_path` fixé.
- **Invitations** : jeton de 244 bits, usage unique, réservation atomique (`update … where used_at is null`).
- **Photos** : bucket privé, chemins `<salon>/<place>/<uuid>`, URL signées ; quota vérifié à l'écriture.
- **Temps réel** : canaux `room:<salon>:…` privés, règle de lecture/écriture par salon ; `postgres_changes`
  sur `salons` filtré par la RLS.
- **Rappels** : `rappel-veille` refuse tout appel sans `x-cron-secret` ; secret et URL dans Vault, pas en clair
  dans `cron.job` (vérifié) ; `call_rappel_veille` non exécutable par les visiteurs.
- **Client** : aucun `dangerouslySetInnerHTML`, `eval` ni `innerHTML` avec des données (seulement deux pages
  de développement à contenu fixe) ; prénoms et textes rendus par React ou PixiJS `Text` (pas de HTML) ;
  `<img src>` ne peut pas exécuter de script. Le service worker ne met jamais en cache Supabase ni les photos.
- **Secrets** : aucun secret dans le code ni dans l'historique (353 commits, recherche de clés service_role,
  `sb_secret_`, JWT, clés privées, jetons GitHub). Seules la clé publishable et la clé VAPID publique sont
  dans le workflow : publiques par nature. Pas de fichier `.env` suivi.
- **Dépendances** : `npm audit` 0 vulnérabilité ; analyse statique semgrep (règles JS de Trail of Bits) sans résultat.
- **Edge Function déployée** `salons` : identique au dépôt.

## Limites de l'audit

- **Aucun test actif** : le site GitHub Pages et l'API Supabase n'étaient pas joignables depuis l'environnement
  d'audit, et la consigne était de ne rien écrire. Les scénarios SEC-01 à SEC-04 sont démontrés par la lecture du
  code et de l'état réel de la base, pas par une attaque réelle.
- **Non lisibles en SQL** : réglages Auth (inscriptions désactivées, limites de débit, durée des sessions), schémas
  exposés par l'API, option « Allow public access » du Realtime, secrets GitHub et secrets des Edge Functions
  (valeur et force du `CRON_SECRET`), comportement exact de `x-forwarded-for` sur Supabase.
- Le registre de règles semgrep en ligne était inaccessible : seules les règles locales de Trail of Bits ont tourné.
- Revue des jeux (`src/games/`) limitée aux points d'injection et au stockage ; logique de score non auditée.
