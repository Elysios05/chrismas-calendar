- Piste : partir de `[]` et lire l'état depuis le backend une fois branché.

**B2. Deux workflows de déploiement GitHub Pages concurrents.**

### P2 — défauts visibles

Le terrain ne couvre pas toute la largeur à cette échelle. Capture : [rapport-2026-11-18/3-bord-du-monde-nuit-ordinateur.jpg](rapport-2026-11-18/3-bord-du-monde-nuit-ordinateur.jpg)

**V2. Lisibilité.**
- Le nom du monde (`.zone-pill`, texte blanc avec une ombre légère) est illisible sur la neige claire : « La Forêt et le Lac gelé », « Le Pôle Nord ».
- Les pastilles des cases verrouillées (blanc sur neige blanche, numéro gris clair) se perdent.
- La nuit, le cadeau du jour s'assombrit comme le reste (palette `c()` appliquée au cadeau) : on le distingue mal alors que c'est l'élément à toucher.
- Capture : [rapport-2026-11-18/4-contraste-etiquettes-mobile.jpg](rapport-2026-11-18/4-contraste-etiquettes-mobile.jpg)

**V3. Sur téléphone, l'en-tête occupe environ le quart supérieur de l'écran** (titre, joueurs, ☀️ et 📍 sur deux rangées, plus le nom du monde, ≈ 215 px sur 844). Des pastilles passent dessous, par exemple la case 21 en bas de page.

### P2 — performance

**F1. Chaque changement d'état reconstruit toute la scène.** `Scene.build()` détruit et redessine le terrain, les ~850 objets et les personnages.
- Ce qui la déclenche : `setStates` (ouverture d'une case, changement de joueur) et `setNight`. La bascule nuit la déclenche même **deux fois** (`App.tsx` : `setNight()` puis `sync()` → `setStates()`).
- Mesure : 0,5 s de gel en CPU ×1, 1,1 s en CPU ×4, découpé en tâches longues de 350 à 600 ms.
- Piste : ne recréer que le cadeau qui change, et teinter plutôt que redessiner pour la nuit.

**F2. Budget par image serré sur un téléphone moyen.** Le JS par image atteint 15,3 ms en CPU ×4, alors que le budget est de 16,7 ms. Tout le monde est dessiné à chaque image, sans élagage (`cullable`) ni mise en cache par monde, en résolution ×2 avec anticorrélation (antialias). S'y ajoutent les 260 flocons et les `Graphics` du voile et de la tempête, vidés et redessinés à chaque image. À vérifier sur un vrai téléphone : SwiftShader ne permet pas de juger le coût GPU (1 à 3 img/s ici, non représentatif).

**F3. La marche des personnages dépend de la fréquence d'images.** `Scene.walkTo` avance d'un pas fixe par `requestAnimationFrame`. Conséquences : deux fois plus vite sur un écran à 120 Hz, et très lent si le téléphone rame. Il faut multiplier le pas par le temps écoulé.

### P3

- Le chunk principal fait 546 Ko (Pixi + React + Supabase + Tone, non découpés) : charger l'audio et les jeux à la demande (`import()`).
- Fredoka vient de Google Fonts sans police de repli métrique. Si la police n'est pas chargée, les numéros des cases sont rendus dans la police par défaut (le `try/catch` de `document.fonts.load` masque l'échec).
- `oxlint` : 5 avertissements (`set-state-in-effect` dans `Mascot.tsx`, `only-export-components` dans `games/quiz`, `ui/dev`, `games/dev`).

## Comment les cadeaux sont visés (hook de test)

Les cadeaux sont dessinés dans le canvas. Pour les viser, les tests utilisent le crochet officiel des outils de dév PixiJS (`globalThis.__PIXI_APP_INIT__`), injecté avant le chargement. Ils parcourent ensuite l'arbre Pixi : les conteneurs interactifs portant `meta`, dont le numéro est lu dans le `Text`. Cela marche sans toucher au code, mais reste fragile si la structure d'un cadeau change.

**Demande à l'équipe Monde** : exposer en mode dev/test une petite API stable, par exemple :

```ts
window.__calendrier = { giftScreenPos(day): {x, y} | null, giftState(day), scrollForDay(day) }
```

## Lancer les outils

```bash
npm run qa:captures   # build + captures (~20 min sous SwiftShader). Options : QA_JOURS=1,9,24 QA_APPAREILS=mobile QA_SANS_BUILD=1
npm run qa:e2e        # Playwright, ~5 min ; QA_TRACE=1 pour garder une trace en cas d'échec
npm run qa:perf       # perf mobile CPU ×4 (QA_CPU=6 pour plus lent)
npm run qa:tout       # les trois
```

Notes :
- Chrome : `/usr/bin/google-chrome` (ou `QA_CHROME`). Port 4180 (ou `QA_PORT`).
- Fredoka est servie localement par `@fontsource/fredoka`, car Google Fonts est injoignable en test.
- `qa:e2e` tourne en DPR 1 pour la vitesse. Les captures sont en DPR 2.
